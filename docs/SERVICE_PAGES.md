# サービスページ（/services/[slug]）仕様

最終更新: 2026-10-03（ヘッダー・フッターの案内とサイトマップを追加）／10-01 夜（9→7ページに組み替え。Instagram初期構築を SNS運用代行の「立ち上げだけ」プランに統合）

## このページは何のためにあるか

**記事や検索から来た人に、資料をダウンロードさせて連絡先を取るためのページ。**
その場で契約させるページではない。CTAの壁を下げて、営業できるリストを溜めることが仕事。

判断の背景は「サイト設計マップ」に記録している。いま何がどう作ってあるかの地図は `docs/SITE_STRUCTURE.md` §4。

---

## いちばん大事な前提

**器は1枚しか作らない。中身はデータで差し替える。見た目は全ページ共通で、違うのは文字だけ。**

```
app/services/[slug]/page.tsx        ← ページの器（メタ情報・構造化データ・静的生成）
components/service/ServicePage.tsx  ← 表示と動き。これ1枚
        ↑ 読み込む
lib/services/index.ts               ← 一覧（list）。ここに1行足すとページが1つ増える
lib/services/<slug>.ts              ← サービスごとの中身（データ）。1ページ1ファイル
lib/services/types.ts               ← データの形（Service 型）
```

**サービスを増やすときに、HTMLもCSSもコンポーネントも書かない。**

## ヘッダー・フッターの案内とサイトマップ（2026-10-03 代表決定）

**「1ページ1ゴール・回遊させない」は、本文の中で他ページへのクリックを促さないという意味。**サイトにあるページは、ヘッダーとフッターで普通に案内する。本文（FV〜FAQ・資料請求パネル）には他ページへのリンクを足さない。

- 案内のサービス一覧は `app/layout.tsx` が `lib/services` の `serviceSlugs`（＝`list` の並び順）と `label` から作り、`components/SiteNav.tsx` の `SiteNavProvider` で全ページに渡す。**手で並べない。**`list` に1行足せば、ヘッダー・フッター・サイトマップに自動で出る
  - ヘッダー・フッターから `lib/services` を直接 import しない（サービス7本ぶんの文言 約170KB がブラウザ側のJSに入る）。layout から名前とURLだけを渡す
- **ヘッダー**（components/SiteHeader.tsx。サイト共通の1種類のまま）
  - PC：右側に「サービス ▾」（押すと7本の一覧が下に開く）・「会社案内」（/）・「お問い合わせ」（/contact）。控えめな文字のリンク（12px・薄い色）。資料請求パネルがいちばん目立つ、を崩さない
  - 一覧はボタンの右端にそろえて左へ開く。右端の資料請求パネル（`.rail`）に重ならない（1280幅でパネル左端920px・一覧の右端718px）
  - 右にパネルが無いページ（cta=true）は「相談する」ボタンが /contact なので、文字の「お問い合わせ」は出さない
  - スマホ（760px以下）：「メニュー」ボタン1つ。開くとサービス7本・会社案内・お問い合わせ。開いている間はヘッダーに白い板を敷き、下の固定バー（`.mbar`）より手前に出す
  - キーボード：ボタンは aria-expanded／aria-controls。Esc で閉じて押したボタンに戻る。Tab で外へ出たら閉じる。外を押しても閉じる。ページが変わったら閉じる
  - 今いるページは aria-current="page"（サービスページでは「サービス」も濃くする）
  - prefers-reduced-motion では開く動きを止める
- **フッター**（components/SiteNav.tsx の `SiteFooterNav`。見た目は components/site-footer.css）
  - トップ・サービスページの `lpfoot`：会社名・住所・メール → サービス7本（2列）｜会社（会社案内・お問い合わせ）→ **法務3ページ（利用規約・特商法・プライバシーポリシー）** → ©
  - 法務3ページ（components/LegalLayout.tsx）：既存のフッターに**サービス7本だけ**を1行で差し込んだ（`<SiteFooterNav only="services" />`）。LegalLayout は main 側が正なので、それ以外は変えていない
  - 記事・会社概要・実績・お問い合わせ（古い作り）のフッターは各ページに直書きで、まだサービスの案内は無い
- **サイトマップ**（app/sitemap.ts）：静的ページ＋**サービス7本（`serviceSlugs` から自動）**＋記事（microCMS）

## サービスを1つ増やす手順

### 1. `lib/services/<slug>.ts` を1ファイル足す

形は `lib/services/types.ts` の `Service` 型。主な項目：

| 項目 | どこに出るか |
|---|---|
| `slug` | URL（`/services/<slug>`） |
| `label` | ヘッダー（現在地・サービス一覧）・フッターのサービス一覧・FVの一番上。短く |
| `metaTitle` / `metaDescription` | 検索結果 |
| `title`（2行）・`titleHighlight` | FVの見出し。`titleHighlight` は `title[1]` の中にそのまま含まれる語 |
| `lede` / `termline` | FVの本文／用語の補足（620px以下では出さない） |
| `facts`（2〜3個） | FVの数字の欄。`v` に数字があれば等幅、無ければ見出し書体。`unit` は12字以内が目安 |
| `points`（3つ） | FVの要点 |
| `problems` / `concept` | 01 こんな状態ではありませんか |
| `gains` | 02 何が変わるか |
| `proof` / `proofNote` | 03 実績（先頭2件はFVにも出る） |
| `deliverables` | 04 何をお渡しするか |
| `excludes` | 05 含まないもの（空なら出ない） |
| `steps` | 06 進め方（2つ以上ならプラン切り替え） |
| `price` | 07 料金。`kind: 'fixed'`（金額）か `'quote'`（何で決まるか） |
| `faq` | 08 よくある質問 |
| `voice` | お客様の声（裏付けのあるものだけ。無ければ null） |
| `docPitch` | 資料請求パネルの「何が届くか」。title 20字・items 4〜5個・各30字以内が目安 |
| `doc` | 配布資料のファイル名。未作成なら null |

### 2. `lib/services/index.ts` に1行足す

```ts
import { service as instagramReel } from './instagram-reel';
// …
const list: Service[] = [ /* … */, instagramReel ];
```

### 3. ビルドして確認

```bash
npm run build                                   # generateStaticParams が自動で新しいURLを拾う
RESEND_API_KEY= npx next start -p 3011          # メール送信キーを空にして起動する（下の「確認の手順」）
```

### 注意点

- `titleHighlight` は `title[1]` の中に**そのまま含まれる文字列**にすること。一致しないと下線が引かれない
- 実績の数字（「150万回」「6万回以上」「1,000本以上」など）は器が自動で等幅の太字にする。
  FVの要約は、`proof.t` に数字が無ければ `proof.d` から数字のかたまりを**そのまま**抜き出して出す（言い換えない）。
  だから `d` の数字は「何の数字か」が分かる書き方にする（例「広告なしで150万回見られた動画があります」）
- `price.monitor` の一文目（最初の「。」まで）は資料請求パネルにも出る。FVには、同じ金額が `lede` に無いときだけ出る
- `voice` に載せる会社名は**掲載許可が取れてから**

## 資料（PDF）のつなぎ方

### いまの状態

`doc: null` のとき、フォーム送信後の動きはこうなる。日数は全部同じにしてある（変えるときは全部直す）。

- 送信ボタンの下（送る前）：「ご入力のメールアドレスに、担当より2営業日以内に資料をお送りします。」
- お客様への返信メール（route.ts）：「担当より2営業日以内にお送りいたします」
- 送信後の表示：「担当より2営業日以内に資料をお送りします」
- 社内通知メール：「**資料PDFが未登録のため、担当者から手動で送付してください**」と警告が出る

### 資料を作ったら

1. PDFを `public/docs/` に置く（例: `public/docs/sns-management.pdf`）
2. `lib/services/<slug>.ts` の `doc` にファイル名を書く

**これだけで自動的に切り替わる。**

- 送信ボタンの下の一行が「送信するとすぐに資料が開きます。同じ資料のリンクをメールでもお送りします。」になる
- 返信メールにダウンロードボタンが入る
- 送信完了と同時にブラウザがダウンロードURLへ遷移する
- 社内通知の警告が消える

### 資料の保護について

`public/docs/` に置いたPDFは、**URLを知っていれば誰でもダウンロードできる**。
フォームを回避されたくない場合は、推測しにくいファイル名にする（例: `sns-management-a3f9c1.pdf`）。
厳密にやるなら Supabase Storage の署名付きURLに変える必要があるが、現状は未対応。

## 資料請求フォームの仕組み

```
ブラウザ（ServicePage.tsx のフォーム）
        │  送る前に画面で確かめる（必須3つ・メールの形）→ 欄の下に日本語で理由
        │  会社名・お名前・メール・(サイトURL・電話)・どのサービスか
        ▼
POST /api/document  （runtime = 'edge'）
        ├─▶ Supabase  inquiries テーブルに保存
        ├─▶ Resend    お客様へ自動返信
        ├─▶ Resend    社内へ通知
        └─▶ Slack     通知（SLACK_WEBHOOK_URL がある場合）
        ▼
成功したら GA4 に generate_lead（gtag があるときだけ）
```

### 入力項目

| 項目 | 必須 | 備考 |
|---|---|---|
| 会社名・屋号 | **必須** | |
| お名前 | **必須** | |
| メールアドレス | **必須** | |
| サイトかSNSのURL | 任意 | 「＋ サイトのURL・電話番号も伝える（任意）」に畳んである |
| 電話番号 | 任意 | 同上。必須にすると入力率が落ちるため任意 |

狭い画面（1040px以下）は入力欄の文字を16pxにしている（iPhoneで触れたとき拡大されないように）。

### 保存先

**専用テーブルは作っていない。** お問い合わせと同じ `inquiries` テーブルに、
`status = 'document_request'` で記録している。

| カラム | 入る値 |
|---|---|
| `name` | お名前 |
| `email` | メールアドレス |
| `company` | 会社名 |
| `content` | `【資料請求】サービス名` / `サービス: slug` / `電話番号: ...` / `サイト: ...` を改行でつないだもの |
| `status` | `document_request`（お問い合わせは `pending`） |

**資料請求だけを抽出するとき**は `status = 'document_request'` で絞る。

### 失敗したときの返し方（route.ts）

画面に出る文言は日本語だけ。

| 場合 | 返すもの |
|---|---|
| 入力の誤り（zod） | 400 `{ error, field }`。画面はその欄の下に出す |
| 表示から3秒未満 | 400「送信が早すぎたため…もう一度押してください」 |
| 見えない欄（honeypot）に入力 | 成功に見せて何もしない |
| 保存とメールを**両方試して両方失敗** | 500「info@dp-guild.com までメールでご連絡ください」（リードを黙って消さない） |
| 保存もメールも未設定（開発環境） | 成功扱い |

### 計測

送信が成功したら、`window.gtag` があるときだけ `gtag('event','generate_lead',{ service: slug })` を送る。
GA4 の管理画面で `generate_lead` をキーイベントに登録すると、サービスページごとの資料請求数が取れる（登録は未実施）。

### 環境変数

すべて未設定でもページは動く（保存・送信をスキップするだけ）。

| 変数 | 用途 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | 保存 |
| `RESEND_API_KEY` | メール送信 |
| `COMPANY_EMAIL` | 送信元・社内通知の宛先（既定 `contact@dp-guild.com`） |
| `COMPANY_NAME` | 送信者名（既定 `株式会社DP-GUILD`） |
| `SLACK_WEBHOOK_URL` | Slack通知 |
| `NEXT_PUBLIC_SITE_URL` | 資料URLの組み立て（既定 `https://dp-guild.com`） |

## 見た目と動きの設計

変えるときに壊しやすいところだけ書く。

### 画面で一番目立たせるのは資料請求パネル

見出しではない。記事から来た人にさせたいのは**資料のダウンロード1つだけ**。

- パネルは**画面の右端に貼り付いた全高の面**。箱にしない（上・右・下の余白ゼロ）
- パネルの中だけスクロールする（`overflow-y:auto`）。**画面が低くても送信ボタンに必ず届く**
- 高さ940px以下のPCは項目名を入力欄の左に置いて縦を詰め、送信ボタンまで1画面に収める
- 白文字が乗るパネル上部のグラデーションは、小さい白文字で4.5:1以上になる濃さにしてある
- **同時に見える申込みの入口は1つ。** 広い画面は右の送信ボタンだけ（FVの「まずは右の資料を →」はボタンではない一行）。
  狭い画面は下の固定バーだけで、資料請求の欄が画面に入っている間と送信後はバーを隠す

### 動く順番で視線を運ぶ

人は**最後に動いたもの**を見る。だから最後に動かすものを、いちばん読ませたい場所の隣に置く。

| 順番 | 動くもの | 終わる時刻 |
|---|---|---|
| 1 | 立方体の線（1本ずつ引かれて組み上がる） | 約0.85秒 |
| 2 | 見出し・本文・数字の欄・実績・要点（`data-fd` の順） | 約0.85秒 |
| 3 | **左下の一行「まずは右の資料をご覧ください →」の矢印** | 1.1秒から3回だけ動いて止まる |

- **FVは CSS だけで出す。** JS（ハイドレーション）を待たない。JS が無い・遅い環境でも白紙にならない
- 右のパネルは**最初から表示**。あとから動かすと視線が右へ飛ぶ
- 立方体は 1041px 以上でスクロールに合わせて分解する。狭い画面は見出しの右上に小さく回り込ませ、動かさない（文字の上を横切るため）

### 出現処理は監視ではなく掃引

2画面目以降の出現に `IntersectionObserver` は使っていない。**アンカーで飛ぶと、飛ばされた要素が
非表示のまま永久に残る**ため。スクロールイベントで残りを掃引する方式にしている。

掃引は `requestAnimationFrame` の外で呼んでいる。rAFが止まる環境（バックグラウンドタブ等）でも本文が出るようにするため。
JS が無いときは page.tsx の `<noscript>` で全部最初から表示する。

### 背景の格子

FVが見えている間だけ rAF で動かす。FVを過ぎたら・裏のタブになったら止める。620px以下は静止した1枚だけ描く。
`prefers-reduced-motion: reduce` では出さない。

### CSSのスコープ

`app/services/[slug]/service.css` は**すべて `.lp.svc` 配下に閉じてある**。共通部分は `app/lp-base.css`（トップ・他LPと共有なので、サービスページだけの変更はここに書かない）。

ダークモード指定は**意図的に外している**。サイト全体が明るいため、このページだけ暗転すると浮くため。

### 重なり順

`.shell` が `z-index:4`、フッターが `z-index:2`。
**この順序を崩すとフッターが資料請求パネルを縦に切る。**

## やらないこと

過去に実際にやらかして直したもの。繰り返さないための記録。

- **内部メモをページに載せない。**「要確認」等の作業用の印は成果物に出さない
- **飾りの英語ラベルを使わない。** PRICE / FREE DOCUMENT のような英語は
  パッと見て意味が入らない。日本語にする（料金／無料）。
  ただし数字（金額・番号）は等幅フォントのままでよい
- **価格をカウントアップさせない。** 途中で止まると誤った金額が表示される
- **画面より高い要素を追従させない。** 送信ボタンに到達できなくなる
- **飾りを画面の先頭に置かない。** 狭い画面で文字が押し下げられる
- **画面の真ん中に空白を作らない。** どこへ行けばいいか分からなくなる
- **申込みの入口を同時に2つ見せない。**（DESIGN_PROMPT「CTAは同時に見えるのが1つ」）
- **FVの表示を JS に頼らない。** JS が無い・遅いと白紙になる

## 確認の手順

見た目を変えたら、最低限これを通す。

```bash
npm run build                                # 型とビルドの検証
RESEND_API_KEY= npx next start -p 3011       # 必ずメール送信キーを空にして起動する
```

`.env.local` には本物のメール送信キーがある。キーを入れたまま起動して送信すると、**実際に社内と入力したアドレスへメールが飛ぶ**。

1. **複数の画面サイズで見る。** 1280×720 / 900×620 / 390×700 と、1280幅の全体。
   自分の画面1つで「収まった」と判断しない
2. **横スクロールバーが出ないこと**
3. **送信ボタンが画面内に入ること**（広い画面はどの高さでも）
4. **JS を切っても本文が読めること**（白紙にならない）
5. **APIを叩く確認は、`RESEND_API_KEY` を空にした環境でのみ行う**（正常系・ハニーポット・3秒未満・不明サービス・メール未入力）。
   キーが入っている環境（`.env.local` そのまま・本番）では叩かない。Supabase・Slack の変数が入っている環境も同じ（保存・通知が本物に飛ぶ）
