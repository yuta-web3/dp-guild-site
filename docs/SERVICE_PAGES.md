# サービスページ（/services/[slug]）仕様

最終更新: 2026-09-10

## このページは何のためにあるか

**記事や検索から来た人に、資料をダウンロードさせて連絡先を取るためのページ。**
その場で契約させるページではない。CTAの壁を下げて、営業できるリストを溜めることが仕事。

判断の背景は「サイト設計マップ」に記録している。実装だけを知りたい場合は本書で足りる。

---

## いちばん大事な前提

**器は1枚しか作らない。中身はデータで差し替える。**

```
app/services/[slug]/page.tsx   ← ページの器。これ1枚だけ
        ↑ 読み込む
lib/services.ts                ← サービスごとの中身（データ）
```

`/services/instagram-feed` は `services['instagram-feed']` を読んで描画している。
**サービスを増やすときに、HTMLもCSSもコンポーネントも書かない。**

## ファイル構成

| ファイル | 役割 | 触る頻度 |
|---|---|---|
| `lib/services.ts` | サービスの中身（文言・価格・納品物・FAQ など） | **サービス追加のたび** |
| `app/services/[slug]/page.tsx` | ページの器。メタ情報・構造化データ・静的生成 | ほぼ触らない |
| `components/service/ServicePage.tsx` | 表示と動き（クライアント側） | 見た目を変えるとき |
| `app/services/[slug]/lp.css` | 見た目。`.lp` 配下に閉じてある | 見た目を変えるとき |
| `lib/document-schema.ts` | 資料請求フォームの入力チェック | 項目を変えるとき |
| `app/api/document/route.ts` | 資料請求の受け口 | 保存先・通知を変えるとき |
| `public/docs/*.pdf` | 配布する資料 | 資料を作ったとき |

## サービスを1つ増やす手順

### 1. `lib/services.ts` にデータを1件足す

`services` オブジェクトにキーを足すだけ。キーがそのままURLになる。

```ts
services['instagram-reel'] = {
  slug: 'instagram-reel',              // URL: /services/instagram-reel
  label: 'Instagram初期構築 ／ 動画',   // ヘッダーと料金欄に出る短い名前
  metaTitle: '...',                    // 検索結果のタイトル
  metaDescription: '...',
  title: ['1行目', '2行目'],            // 見出し。2行に分けて渡す
  titleHighlight: '下線を引く語',       // title[1] の中の一部と必ず一致させること
  lede: ['1行目', '2行目'],
  termline: '用語の補足。不要なら null',
  price: 300000,                       // 数値。表示は自動でカンマ区切りになる
  priceNote: '円（税別）',
  delivery: '9投稿',                    // 数字と単位を含む文字列。自動で分解して表示する
  period: '3–4週間',                    // 同上
  points: ['...', '...', '...'],
  problems: ['...', '...', '...'],     // 01「こんな状態ではありませんか」
  gains: [{ t: '見出し', d: '説明' }],   // 02「何が変わるか」
  deliverables: [{ t: '...', d: '...' }], // 03「何をお渡しするか」
  excludes: ['...'],                    // 04「含まないもの」
  steps: [{ t: '...', d: '...' }],      // 05「進め方」
  planItems: ['...'],                   // 06「料金」の箇条書き
  planNote: ['...'],                    // 料金の下の補足（複数行可）
  faq: [{ q: '...', a: '...' }],        // 07「よくある質問」
  voice: { who: '...', quote: '...', meta: '...' },  // 08「お客様の声」。無いなら null
  doc: null,                            // 配布資料のファイル名。後述
};
```

### 2. ビルドして確認

```bash
npm run build          # generateStaticParams が自動で新しいURLを拾う
npx next start -p 3000 # http://localhost:3000/services/instagram-reel
```

**これで終わり。** 他のファイルは触らない。

### 注意点

- `titleHighlight` は `title[1]` の中に**そのまま含まれる文字列**にすること。
  一致しないと下線が引かれず、見出しが崩れる。
- `delivery` と `period` は「数字＋単位」の形にすること。
  表示側で数字だけ大きくするため、正規表現で分解している。
- `voice` に載せる会社名は**掲載許可が取れてから**。
  取れていない間は「サービス業／滋賀県」のように業種と地域で書く。

## 資料（PDF）のつなぎ方

### いまの状態

`doc: null` のとき、フォーム送信後の動きはこうなる。

- お客様への返信メール：「担当より1営業日以内にお送りします」
- 社内通知メール：「**資料PDFが未登録のため、担当者から手動で送付してください**」と警告が出る
- ページ上の完了表示：「担当より1営業日以内に資料をお送りします」

### 資料を作ったら

1. PDFを `public/docs/` に置く（例: `public/docs/instagram-feed.pdf`）
2. `lib/services.ts` の該当サービスの `doc` にファイル名を書く

```ts
doc: 'instagram-feed.pdf',
```

**これだけで自動的に切り替わる。**

- 返信メールにダウンロードボタンが入る
- 送信完了と同時にブラウザがダウンロードURLへ遷移する
- 社内通知の警告が消える

### 資料の保護について

`public/docs/` に置いたPDFは、**URLを知っていれば誰でもダウンロードできる**。
フォームを回避されたくない場合は、推測しにくいファイル名にする（例: `instagram-feed-a3f9c1.pdf`）。
厳密にやるなら Supabase Storage の署名付きURLに変える必要があるが、現状は未対応。

## 資料請求フォームの仕組み

```
ブラウザ（ServicePage.tsx のフォーム）
        │  会社名・お名前・メール・電話・どのサービスか
        ▼
POST /api/document  （runtime = 'edge'）
        ├─▶ Supabase  inquiries テーブルに保存
        ├─▶ Resend    お客様へ自動返信
        ├─▶ Resend    社内へ通知
        └─▶ Slack     通知（SLACK_WEBHOOK_URL がある場合）
```

### 入力項目

| 項目 | 必須 | 備考 |
|---|---|---|
| 会社名 | **必須** | |
| お名前 | **必須** | |
| メールアドレス | **必須** | |
| 電話番号 | 任意 | 必須にすると入力率が落ちるため任意 |

### 保存先

**専用テーブルは作っていない。** お問い合わせと同じ `inquiries` テーブルに、
`status = 'document_request'` で記録している。

| カラム | 入る値 |
|---|---|
| `name` | お名前 |
| `email` | メールアドレス |
| `company` | 会社名 |
| `content` | `【資料請求】サービス名` / `サービス: slug` / `電話番号: ...` を改行でつないだもの |
| `status` | `document_request`（お問い合わせは `pending`） |

**資料請求だけを抽出するとき**は `status = 'document_request'` で絞る。

将来リード数が増えて分けたくなったら専用テーブルへ移すが、
その場合は `app/api/document/route.ts` の insert 先を変えるだけで済む。

### スパム対策

2つ入れている。どちらも `/api/contact` と同じ方式。

1. **ハニーポット** … 画面に見えない入力欄（`.hp`）。値が入っていたら弾く
2. **3秒ガード** … ページ表示から3秒未満の送信を弾く

### 環境変数

すべて未設定でもページは動く（保存・送信をスキップするだけ）。

| 変数 | 用途 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | 保存 |
| `RESEND_API_KEY` | メール送信 |
| `COMPANY_EMAIL` | 送信元・社内通知の宛先（既定 `contact@dp-guild.com`） |
| `COMPANY_NAME` | 送信者名（既定 `株式会社DP-GUILD`） |
| `SLACK_WEBHOOK_URL` | Slack通知 |
| `NEXT_PUBLIC_SITE_URL` | 資料URLの組み立て（既定 `https://dp-guild.com`） |

## 見た目と動きの設計

変えるときに壊しやすいところだけ書く。

### 画面で一番目立たせるのは資料請求パネル

見出しではない。記事から来た人にさせたいのは**資料のダウンロード1つだけ**。
見出しが一番強いと視線がそこで止まって終わる。

- 見出しは 26px まで落としてある
- パネルは**画面の右端に貼り付いた全高の面**。箱にしない（上・右・下の余白ゼロ）
- パネルの中だけスクロールする（`overflow-y:auto`）。
  **画面が低くても送信ボタンに必ず届く**ので、追従の可否を判定する処理は不要

### 動く順番で視線を運ぶ

人は**最後に動いたもの**を見る。だから最後に動かすものを、いちばん読ませたい場所の隣に置く。

| 順番 | 動くもの | 終わる時刻 |
|---|---|---|
| 1 | 背景の9枚タイル（先に片付ける） | 約0.85秒 |
| 2 | 見出し・本文・料金・要点 | 順に |
| 3 | **左下の一言「まずは資料をご覧ください →」** | 約1.22秒 |

- タイルは**右下から始めて最後に左上**に置く（`TILE_ORDER`）。
  最後の1枚が見出しの隣に落ちるので、そのまま文章へ目が行く
- 右のパネルは**最初から表示**。あとから動かすと視線が右へ飛ぶ
- 矢印は3回だけ動いて止まる。動き続けさせない

### 出現処理は監視ではなく掃引

`IntersectionObserver` は使っていない。**アンカーで飛ぶと、飛ばされた要素が
非表示のまま永久に残る**ため。スクロールイベントで残りを掃引する方式にしている。

掃引は `requestAnimationFrame` の外で呼んでいる。
rAFが止まる環境（バックグラウンドタブ等）でも本文が出るようにするため。

### CSSのスコープ

`app/services/[slug]/lp.css` は**すべて `.lp` 配下に閉じてある**。
`:root` や `body` への指定は `.lp` に置き換えてあるので、既存ページに影響しない。

ダークモード指定は**意図的に外している**。サイト全体が明るいため、
このページだけ暗転すると浮くため。

### 重なり順

`.shell` が `z-index:4`、フッターが `z-index:2`。
**この順序を崩すとフッターが資料請求パネルを縦に切る。**

## Stripe審査で見られる項目

このページは決済導入の前提でもある。以下を満たすように作ってある。

| Stripeの要求 | 対応箇所 |
|---|---|
| サービスの詳細な説明 | 納品物・含まないもの・進め方 |
| 価格と通貨の明示 | 料金セクション ＋ `Schema.org` の `Offer`（`priceCurrency: JPY`） |
| 返金・キャンセルポリシー | 料金セクションから利用規約 第6条へリンク |
| 複数の問い合わせ手段 | 資料請求フォーム ＋ `/contact` ＋ メールアドレス（フッター） |
| プライバシーポリシー | フッターからリンク |

**法務3ページへのリンクはフッターに必ず残すこと。** 消すと審査で指摘される。

## やらないこと

過去に実際にやらかして直したもの。繰り返さないための記録。

- **内部メモをページに載せない。**「要確認」等の作業用の印は成果物に出さない
- **飾りの英語ラベルを使わない。** PRICE / FREE DOCUMENT のような英語は
  パッと見て意味が入らない。日本語にする（料金／無料）。
  ただし数字（金額・番号）は等幅フォントのままでよい
- **価格をカウントアップさせない。** 途中で止まると誤った金額が表示される
- **画面より高い要素を追従させない。** 送信ボタンに到達できなくなる
- **飾りを画面の先頭に置かない。** 狭い画面で文字が押し下げられる
- **画面の真ん中に空白を作らない。** どこへ行けばいいか分からなくなる

## 確認の手順

見た目を変えたら、最低限これを通す。

```bash
npm run build                       # 型とビルドの検証
npx next start -p 3000
```

1. **複数の画面サイズで見る。** 1280×720 / 900×620 / 390×700 は必ず。
   自分の画面1つで「収まった」と判断しない
2. **横スクロールバーが出ないこと**
3. **送信ボタンが画面内に入ること**（どの高さでも）
4. **APIを叩く**（正常系・ハニーポット・3秒未満・不明サービス・メール未入力）

```bash
curl -X POST http://localhost:3000/api/document \
  -H "Content-Type: application/json" \
  -d '{"company":"テスト","name":"山田","email":"t@example.com","phone":"",
       "service":"instagram-feed","honeypot":"","timestamp":0}'
```
